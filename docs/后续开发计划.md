## 1. 首页状态记忆：返回后不应回退到默认 BiliLive

### 现状
- `HomeViewModel`（`Sources/ChaosSeedApp/Features/Home/HomeViewModel.swift`）持有
  `platform / category / subCategory / keyword / searchKeyword / page / rooms` 等状态。
- 初始化时 `platform = .biliLive`、`category = "recommend"`。
- `selectPlatform(_:)` 会重置 `category / subCategory / keyword / searchKeyword / page`。
- 详情页通过 `onOpenRoom` 回调进入，返回首页后 `HomeViewModel` 实例本身仍在，
  理论上应保留状态；但实际表现是「点击 Huya → 选二级分类 → 进入播放返回 → 切回默认 BiliLive」，
  说明存在某处重置（可能是详情页以全屏覆盖替换了内容列、或根视图重建导致 VM 重建）。

### 目标
- 从详情页（播放）返回首页后，必须停留在用户最后操作的平台与分类，
  例如「Huya × 某二级分类 × 第 N 页」，不得回退到 BiliLive 推荐。
- 切换侧边栏导航（首页 ↔ 历史 ↔ 设置）再回到首页，状态同样保留。
- 进程重启后，平台 / 一级分类 / 二级分类偏好可持久化（写 UserDefaults / SwiftData）。

### 方案要点
- 明确详情页呈现方式：优先用 `.sheet` / `fullScreenCover`（iOS）/ 覆盖层而非替换
  `NavigationSplitView` 的 detail 列，确保 `HomeViewModel` 不被销毁重建。
- 确认 `RootView`（`App/RootView.swift`）中 `HomeView` 与 `homeVM` 的持有关系，
  避免在 `selection` 变化时重新构造 `HomeViewModel`。
- 持久化「上次选中的 platform / category / subCategory」，启动时恢复为默认值来源，
  而非硬编码 `.biliLive / "recommend"`。
- 为「上次浏览位置」引入一个轻量结构体 `HomeBookmark { platform, category, subCategory, page }`，
  存入 `@AppStorage` 或 SwiftData。

### 关联文件
- `Sources/ChaosSeedApp/Features/Home/HomeViewModel.swift`
- `Sources/ChaosSeedApp/App/RootView.swift`
- `Sources/ChaosSeedApp/App/ChaosSeedApp.swift`
- 新增：`Sources/ChaosSeedApp/App/HomeBookmark.swift`（建议）

### 验收标准
- [ ] Huya → 选二级分类 → 进入播放 → 返回，平台仍为 Huya 且二级分类、页码保持。
- [ ] 切到历史 / 设置再回到首页，状态不丢。
- [ ] 退出应用重开，默认恢复上次平台与分类（可由设置开关控制是否记忆）。

## 2. 二级 / 三级分类切换不触发刷新

### 现状
- `HomeViewModel.selectCategory(_:)` 在切换一级分类时会把 `subCategory` 重置为
  该一级分类的第一个子分类，并调用 `load()`。
- `selectSub(_:)` 也会调用 `load()`。
- `loadRooms()`（`HomeViewModel.swift:116`）依据 `platform / category / subCategory`
  计算请求参数：BiliLive 用 `parent_area_id=category & area_id=subCategory`，
  Douyu/Huya 只用 `subCategory`（空则用 `category`）。
- 用户反馈：二级 → 三级（子分类）切换后**不发送请求刷新**。需定位是 UI 未触发回调，
  还是回调触发但请求未发出 / 被旧请求覆盖。

### 目标
- 任意一级 / 二级 / 三级分类切换，必须立即重新拉取对应房间列表并替换网格内容。
- 切换时取消上一个未完成请求（已有 `loadTask?.cancel()`，需确认路径覆盖）。

### 方案要点
- 检查 `HomeView`（`Features/Home/HomeView.swift`）中二级 / 三级分类控件的绑定，
  确认 `onChange` / `onTapGesture` 真正调用到 `selectSub`。
- 确认 BiliLive 三级（area）切换时 `subCategory` 被正确更新且非空；
  若分类树只有两级（一级 area + 二级 area），统一术语，避免「三级」命名歧义。
- 给 `loadRooms()` 增加 `Log.network.debug` 打印每次请求的
  `(platform, category, subCategory, page)`，便于回归验证。
- 单测覆盖：给定 `selectSub("xxx")` 后 `loadRooms` 使用的请求参数正确。

### 关联文件
- `Sources/ChaosSeedApp/Features/Home/HomeViewModel.swift`
- `Sources/ChaosSeedApp/Features/Home/HomeView.swift`
- `Tests/ChaosSeedAppTests/`（新增 `HomeViewModelSelectionTests`）

### 验收标准
- [ ] 二级 / 三级分类点击后，网格内容在 ≤1 次请求内更新。
- [ ] 快速连续切换不会出现「旧数据覆盖新数据」（通过 `loadTask` 取消保证）。
- [ ] 网络日志能看到每次切换对应的请求与参数。

## 3. BiliLive 直播源：对齐 main 分支 chaos-core 的「拿到 URL 后的额外处理」

### 现状
- Swift 侧 `Networking/LivestreamBili.swift` 已移植 `chaos-core` 的 bili_live 主链路：
  buvid cookie 缓存、v2 `getRoomPlayInfo`、v1 `playUrl`、html fallback、
  `pickBestCodec`、`Mbga.sortUrls`（CDN 偏好排序）。
- 但与 `main` 分支 `chaos-core/src/livestream/platforms/bili_live.rs` 逐项对照后，
  仍需校验 / 补齐以下「拿到 URL 后的处理」差异：

  1. **URL 绑定条件**：main 在 `parse_room_playinfo_value` 中，当请求指定 `qn` 时
     只要 `qn` 匹配且 `urls` 非空就绑定（并记 warn，因为部分房间 `current_qn != requested_qn`
     但 URL 其实已切到目标清晰度）。Swift 版以此为兼容基线，并增加 URL 实际 qn 校验，
     避免出现「低清流被标成高画质」。
     - 2026-06-14 实测房间 `545068`：请求 `qn=10000/400` 均返回
       `current_qn=250`，且媒体 URL 查询参数明确为 `qn=250`。Swift 版现优先检查
       URL 中的实际 qn，明确降档时拒绝把低清流挂到高画质 variant；URL 不含 qn 时
       仍保留 main 的兼容行为。
  2. **`resolve_variant_for_qn` 兜底链**：main 的顺序是
     `v2(current_qn==qn 即返回) → v1 playUrl → html fallback → v2 URL 作为最后手段`。
     Swift 版（`biliResolveVariantForQn`）结构一致，需补 warn 日志并对齐边界。
  3. **`fetch_room_play_info` 的请求参数**：main 使用
     `protocol=0,1&format=0,1,2&codec=0,1&platform=web&ptype=8&dolby=5`；
     Swift 版已带 `ptype=8&dolby=5`，需确认 `dolby` 在 macOS 26 / 内置播放器下生效。
  4. **`apply_drop_inaccessible`**：当 `dropInaccessibleHighQualities=true` 时，
     按已解析到的最高 qn 裁掉更高清晰度，避免列表里出现「选了播不了」的档位。
     Swift 版已实现，需把 `ResolveOptions.default` 的默认值与 main 对齐。
  5. **PlaybackHints**：Bili CDN 校验 UA + Referer，`decode_manifest` 已设
     `Referer: https://live.bilibili.com/`，UA 由播放器侧补齐
     （见 `DetailViewModel.effectivePlaybackHints`）。
     需确认 IINA / 内置播放器都正确携带这两项。

### 目标
- 在真实 BiliLive 房间上，解析出的最高可用清晰度 URL 可直接播放、不糊、不被反爬拦截。
- Swift 实现与 `chaos-core` main 分支行为对齐，差异点有单测覆盖。

### 方案要点
- 用 main 分支 `chaos-core/tests/livestream_bili_live_mock.rs` 的 fixture 做对照测试，
  在 Swift 侧用相同 JSON 跑 `biliParseRoomPlayInfoValue` / `biliResolveVariantForQn`，
  断言选中的 codec、绑定的 URL、backupUrls 顺序一致。
- 补齐缺失的 warn / debug 日志，关键字段：`rid / current_qn / requested_qn / codec_name / picked host`。
- 校验 `ResolveOptions` 默认值（尤其 `dropInaccessibleHighQualities`）。
- 若引入内置播放器（见 §5），需在播放器侧再次确认 Referer/UA 注入路径。
- 内置播放器不能仅以 `variant.url != nil` 判断是否完成解析：若现有 URL 为 FLV，
  仍需调用 `resolveVariant` 获取 HLS；否则会跳过 BiliLive 的二次解析。

### 关联文件
- `Sources/ChaosSeedApp/Networking/LivestreamBili.swift`
- `Sources/ChaosSeedApp/Networking/LiveStreamUtils.swift`（Mbga）
- `Sources/ChaosSeedApp/Features/Detail/DetailViewModel.swift`
- `Tests/ChaosSeedAppTests/`（新增 / 扩充 bili fixture 对照测试）

### 验收标准
- [ ] 至少 3 个真实 BiliLive 房间：最高档清晰度可正常播放，画面清晰。
- [ ] 与 main 分支 fixture 对照测试：variant 列表与主 URL 完全一致。
- [ ] `current_qn != requested_qn` 时有 warn 日志且仍能绑定到可播 URL。
- [ ] IINA 与内置播放器均携带正确的 Referer / UA。

## 4. macOS Liquid Glass 深度适配（macOS 26 Tahoe）

### 现状
- `Theme/LiquidGlass.swift` 提供了两个最小封装：
  `liquidGlassBackground(in:)` 与 `liquidGlassBar()`，
  均为 `if #available(macOS 26.0, *) { glassEffect } else { 材质回退 }`。
- 这是「能用」级别，离「足够 Liquid Glass、符合最新 HIG」还有距离。

### 目标
- 最低支持 macOS 26，并全面采用 Liquid Glass 设计语言：工具栏、侧边栏、浮层、卡片、弹幕控制面板
  均使用 `.glassEffect()` 与 `GlassEffectContainer`，体现真实折射与层次。

### 方案要点
- 部署目标统一为 macOS 26，去掉旧系统材质回退，直接使用新 API。
- 用 `GlassEffectContainer` 包裹相邻 glass 元素，避免多重叠加导致的性能 / 视觉割裂。
- 工具栏改用 `.toolbarBackground(.automatic)` + glass，让 NavigationSplitView 的
  侧边栏与详情栏顶部分别呈现玻璃质感。
- 卡片（`Components/CommonComponents.swift`、`CoverImage`）改用
  `liquidGlassBackground(in: .rect(cornerRadius:))`，统一圆角与阴影。
- 详情页清晰度列表、内置播放器控制条、弹幕设置面板（见 §5、§6）全部 glass 化。
- 验证深色 / 浅色、强调色、增加对比度辅助模式下表现。

## 5. 内置播放器：AVFoundation HLS + WebKit HTTP-FLV

### 现状
- 已提供应用内双后端播放器：HLS / MP4 使用 AVFoundation，HTTP-FLV 使用
  WebKit Media Source Extensions + mpegts.js 1.8.0。
- BiliLive 优先二次解析 HLS，Huya 使用接口原生 HLS，Douyu 使用网页接口真实
  HTTP-FLV；P2P `.xs` 不再误判为系统可播放地址。
- `AVPlayer` 在视图生命周期内保持稳定实例，修复播放一段时间或退出播放器时
  AVKit 更新事务触发的崩溃。

### 目标
- 提供应用内置播放器，无需依赖 IINA 也能直接播放解析出的 HLS 与 HTTP-FLV。
- 对系统支持的 HLS、HDR、E-AC-3 / Atmos / Dolby Vision 内容交由 AVFoundation 解码；
  实际输出能力取决于直播源、系统、显示器和音频设备。
- IINA 仍作为「外部播放器」选项保留，用户可在设置里选择默认播放器。

### 方案要点
- 播放核心：`BuiltinPlayer` 按媒体类型选择后端。HLS / MP4 使用稳定的
  `AVPlayer` + `AVPlayerItem`；HTTP-FLV 使用 `WKWebView` 内的 mpegts.js
  转封装到 Media Source Extensions。
- WebKit 页面将 mpegts.js 内联，并把 security origin 设为当前直播 CDN，
  避免 `file://` 页面跨源拉流失败；换清晰度时重建 origin 并过滤旧会话迟到事件。
- HTTP header 注入：`AVURLAssetHTTPHeaderFieldsKey` 设置 Referer / UA，
  对齐 `PlaybackHints`，解决 Bili CDN 校验。
- 音频：不要把 `audioTimePitchAlgorithm` 当作 Atmos 开关；保留系统默认解码路径，
  用真实 E-AC-3 / Atmos 媒体和支持的输出设备验证。
- HDR：`AVPlayerLayer` / `AVPlayerView` 配合 HDR 显示，确认窗口为 HDR 就绪
  （`NSWindow` 的 `colorSpace` / EDR 设置）。
- 权限：检查必要的网络 entitlement；媒体格式支持以 AVFoundation 官方能力为准，沙盒下若受限则评估
  「非沙盒分发」或「辅助扩展」方案。此处需先做可行性调研，再定方案。
- 播放器 UI：SwiftUI 包裹 `AVPlayerView` 或自绘控制条，并预留弹幕 overlay 挂载点（见 §6）。
- 播放器生命周期：`AVPlayerView` 绑定稳定的单个 `AVPlayer`，切清晰度仅替换
  `AVPlayerItem`。不要在 SwiftUI / AVKit 更新事务中把 `AVPlayerView.player` 置空；
  macOS 27 Beta 上该路径已观察到 AVKit 主线程 `SIGTRAP`。

## 6. 内置播放器弹幕：类 BiliBili 的弹幕配置

### 现状
- 已对齐 `main` 分支 `chaos-core` 接入 BiliLive 弹幕：
  真实 room id、WBI `getDanmuInfo` token、WebSocket `op=8` 鉴权、心跳、
  zlib wrapper / raw deflate / Brotli 解包、legacy `DANMU_MSG` 与 `dm_v2`
  protobuf 文本/表情解析。
- 渲染层已使用到达时间驱动的轨道调度，支持滚动、顶部、底部模式与表情图片；
  配置已持久化，并支持关键词/正则屏蔽、彩色开关、透明度过滤和重复折叠。

### 目标
- 为内置播放器叠加实时弹幕层（SwiftUI overlay）。
- 提供类 BiliBili 的弹幕配置面板：
  字号、不透明度、滚动速度、显示区域（1/4 / 半屏 / 全屏）、
  显示模式（滚动 / 顶部 / 底部）、彩色弹幕开关、
  屏蔽词（关键词与正则）、重复弹幕折叠、透明弹幕过滤。

### 方案要点
- 协议层：移植 `chaos-core` 的 `bili_live.rs` / `bili_live_dm_v2.rs` 到 Swift，
  封装 `DanmakuClient`（WebSocket、心跳、proto 解析）。可放
  `Sources/ChaosSeedApp/Networking/Danmaku/`。
- BiliLive 已实现；Douyu/Huya 弹幕仍为后续扩展项。
- 弹幕渲染：SwiftUI `Canvas` / `TimelineView` 或 `AVPlayerLayer` 上层 overlay，
  做碰撞避让与轨道分配（顶部 / 底部 / 滚动三区）。
- 配置项持久化到 `@AppStorage` 或 SwiftData；设置面板复用 Liquid Glass 风格（见 §4）。
- 性能：弹幕量大时做抽帧 / 合并 / 视窗外剔除；考虑 `DisplayLink` 驱动。
- 与内置播放器（§5）共享时间轴，支持「按播放进度回放 / 暂停弹幕」。

## 优先级建议

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | 1. 状态记忆 | 体验基础缺陷，修复成本低 |
| P0 | 2. 分类切换刷新 | 核心浏览路径不可用 |
| P1 | 3. BiliLive URL 处理对齐 | 影响最终播放质量，已有大量代码基础 |
| P1 | 5. 内置播放器（含杜比） | 为弹幕与体验闭环铺路，需先做授权调研 |
| P2 | 6. 弹幕配置 | 依赖内置播放器；体验增强项 |
| P2 | 4. Liquid Glass 深度适配 | 视觉增强项，可随各功能迭代逐步推进 |

> P0 / P1 可并行启动；P2 建议在 P1 内置播放器落地后推进。
